CONCORD

How it works
What problem does it solve?

Anything that stores important data, like orders, payments or messages, keeps copies on several machines so one failure doesn't lose it. The hard part is agreeing on what has really been saved while machines crash and networks split.

If a system says "saved" too early, one failure can erase data a user was told is safe. If the copies disagree about the order of writes, they drift apart.

Concord is a replicated key-value store that makes "confirmed" mean safe: anything it confirms survives the crash or cut-off of any one of its three machines.

What is Raft consensus?

Raft is an algorithm that lets a group of machines agree on one ordered list of changes (a log), even when some of them crash or lose contact. It has three parts:

  • Leader election. The machines vote for one leader. Winning needs votes from a majority, here 2 of 3. Every election starts a new numbered term, so a leader from an old term is recognized and ignored.
  • Log replication. The leader adds each write to its log and sends it to the others. A follower only accepts an entry if its log matches the leader's up to that point, so the logs can't fork.
  • Commit rule. An entry is committed once a majority has stored it. Any two majorities of 3 share at least one machine, so whoever leads next already has every committed entry.

Raft was published by Diego Ongaro and John Ousterhout in 2014 as an easier-to-understand alternative to Paxos. etcd, Consul and CockroachDB use it.

How Concord uses Raft
  • Three machines, one Raft group, fixed membership.
  • Each machine writes to a write-ahead log and forces it to disk (fsync) before it votes or replies, so it never forgets something it agreed to.
  • The leader confirms a write only once a majority has it on disk, and only entries from its own term count. A new leader first writes an empty entry so earlier entries can commit safely.
  • The Raft core is plain, deterministic Rust with no clock or network inside it. That's what lets this page replay a failure exactly. The real servers talk over gRPC.
Tradeoffs
  • Slower confirms. Every write waits for at least one other data center to save it, which adds a network round trip. Async replication answers as soon as the main data center has it.
  • Needs a majority to take writes. If 2 of the 3 data centers are down or cut off, Concord stops accepting writes. It stays correct but becomes unavailable. Async replication keeps going on one machine and risks losing data.
  • More hardware. Surviving one failure takes 3 machines. Surviving two takes 5.
  • Clients may have to retry. A cut-off old leader can't confirm anything, so a customer talking to it waits, then retries elsewhere.
  • Limits of this build. Membership is fixed. Reads come from one machine's copy and can be slightly stale. There's no PreVote, so a flaky cable can trigger repeated elections.
  • When async is the better choice. When speed matters more than losing the last few writes: caches, analytics and metrics.
What this page is

The page runs Concord's real Raft code in a simulator on the server, with a private copy for each visitor. A "power cut" is a simulated crash: what a data center saved to disk survives, and what was only in memory doesn't. Real power loss, disk failure and speed aren't measured here.

1 of 3 · The problem

A "confirmed" order can still disappear

When you buy something online, the store saves your order in a data center and tells you "confirmed".

Most stores copy the order to other data centers a moment later. If the first one loses power before that, your order is gone, even though you were told it was confirmed.

2 of 3 · How Concord fixes it

Only say "confirmed" when 2 of 3 have it

Concord copies every order to 3 data centers, and only tells the customer "confirmed" once at least 2 of them have saved it.

If any one data center goes dark, the order is still safe in another one.
